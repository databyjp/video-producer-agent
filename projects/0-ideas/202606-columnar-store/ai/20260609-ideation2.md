# Video Plan: Search vs. Analytics — Can One Database Do Both?

## Video Idea Evaluation

### Strengths
- **Real tension, not manufactured**: The inverted index vs. columnar storage tradeoff is fundamental CS, and engineers who've had to run ES + ClickHouse (or ES + a data warehouse) side by side will immediately resonate
- **Timely**: Elasticsearch has shipped a *lot* of work in this space recently (LogsDB, TSDS, ES|QL columnar engine, doc value skippers) — this is a "the landscape just changed" story
- **Clear narrative arc**: Generic problem → why it exists → what changed → how ES solved it. This structures itself naturally
- **Competitive angle without being salesy**: You can honestly discuss the tradeoffs (e.g. why ClickHouse/Doris are adding inverted indexes, and why ES is adding columnar processing) — convergence from both sides

### Risks / Things to watch
- **Title #3 is too "solved it"** — feels like an ad. Titles #1 and #2 are stronger because they frame it as a question/tension
- **"Database" vs "Engine"**: I'd go with "Database" for the title (SEO) but clarify "engine" in the video itself
- **Depth calibration**: The primary audience knows what an inverted index is. Don't over-explain the basics — get to the *tension* quickly and spend more time on the ES-specific solutions

### Title recommendation
**"Search vs. Analytics: Can One Database Do Both?"** — strongest hook, clean SEO, frames it as a genuine question

## Key Technical Topics (Narrative Order)

### Act 1: The Fundamental Tension (generic, ~30% of video)

#### 1. What search engines optimize for
- Inverted index: term → document IDs. Optimized for "find documents containing X"
- BM25 scoring (term frequency saturation, length normalization)
- Write overhead: tokenization, posting lists, positions, term frequencies

#### 2. What analytics engines optimize for
- Columnar storage: each field stored as a contiguous array. Optimized for "compute aggregate Y across all documents"
- Compression exploits homogeneity (delta encoding, RLE, dictionary encoding)
- Scans columns, not documents

#### 3. Why they conflict
- Inverted indexes are great at finding needles in haystacks but terrible at scanning/aggregating
- Columnar stores are great at scanning/aggregating but terrible at finding specific documents
- The traditional answer: run two systems (ES + ClickHouse, Solr + Snowflake, etc.) with sync pipelines between them

### Act 2: How Elasticsearch Bridges Both (ES-specific, ~50% of video)

#### 4. Doc values: the columnar layer inside a search engine
- Lucene 4.0 (2012) introduced doc values
- Same data as the inverted index, but stored column-oriented
- Enables sorting, aggregations, and scripting
- Compression: GCD, delta encoding, ordinal tables
- The key insight: doc IDs link the inverted index to the column store — you can search with one and aggregate with the other

#### 5. The IndexOrDocValuesQuery pattern
- Query planner dynamically decides: iterate matches → use the inverted index; verify individual docs → use doc values
- Same query, different execution based on selectivity
- This is the architectural DNA of "one engine, both workloads"

#### 6. LogsDB: pushing columnar storage further
- Index sorting (host.name + @timestamp) makes compression dramatically better
- Synthetic _source: stop storing the raw JSON blob, reconstruct from doc values on demand
- ZSTD compression, TSDB codec (PFOR-delta, cyclic ordinals, RLE)
- Result: 75% storage reduction — approaching purpose-built columnar stores

#### 7. Doc value skippers: replacing inverted indexes where they're not needed
- For TSDS/metrics, inverted indexes on dimensions and @timestamp replaced with hierarchical min/max metadata on doc value blocks
- 10 bytes/datapoint savings
- This is Elasticsearch *choosing* columnar over inverted where it makes sense

#### 8. ES|QL: a columnar query execution engine
- Not a transpilation to Query DSL — a new engine
- Vectorized execution, zero-copy decoding from doc values into compute blocks
- Swiss-style hash tables with SIMD for aggregations
- TS command for native time-series processing
- Result: 30x faster than Prometheus on metrics queries

#### 9. match_only_text and pattern_text
- Stripping BM25 scoring data (term frequencies, positions) from the inverted index when relevance ranking isn't needed (logs)
- pattern_text: decomposing log messages into templates + variables for columnar compression
- Search engine deliberately shedding search overhead for analytics workloads

### Act 3: The Full Picture (synthesis, ~20% of video)

#### 10. Hybrid search: the ultimate "both" answer
- BM25 lexical search + kNN vector search + aggregations, all in one query
- Reciprocal Rank Fusion combines ranked lists from different retrieval methods
- This only works because inverted indexes, doc values, and HNSW graphs all share the same segment/doc-ID space

#### 11. The convergence from both sides
- ES adding columnar processing (LogsDB, ES|QL, doc value skippers)
- Columnar DBs adding inverted indexes (Doris, ClickHouse)
- The future is hybrid architectures that choose the right data structure per-field, per-query

#### 12. When you still need two systems
- Be honest: if your workload is 99% analytical with complex JOINs across many tables, a dedicated OLAP engine is still better
- ES excels when you need search + analytics on the same data, especially time-series/observability/security data
